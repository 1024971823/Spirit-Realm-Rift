## 已执行的本机容量短测

在 Intel Core Ultra 5 336H、12 逻辑 CPU、约 31 GiB 内存的开发机上，用 Node 24.22.3 原生 TypeScript 运行一个网关和四个独立游戏进程；PostgreSQL、Redis 与加载器也在同机。1000 个账号连接、600 人操作、100 个六人房，公开/三种自定义模式混跑，无机器人。五个独立协议加载器各测量至少 210 秒，上下行各用应用计时器增加 30 ms 延迟。

| 指标 | 实测 |
| --- | ---: |
| 每人平均实发输入频率 | 19.828 Hz |
| 输入确认总体 P95 | 133 ms，498,631 个已确认样本 |
| 续局 P95 | 103 ms，95 次成功续局 |
| 最大观测游戏进程滚动帧 P99 | 14.290 ms，包含输入处理 |
| 服务端 CPU 均值 / 峰值 | 146.25% / 177.29%，100% 为一核 |
| 服务端 RSS 峰值 | 1028.13 MiB |
| 服务端向客户端应用层平均带宽 | 687.080 Mbit/s |
| 通用错误计数 | 1，保留原值 |

首轮 100 场对局完成并提交 600 条玩家结果，随后 100 场重新开局；未发现重复 `(match_id,player_id)`。游戏进程及结算失败计数均为 0。唯一通用错误出现在换局窗口，时序及持久结果补查支持“原局结束导致加载器等待续局超时”的解释，但旧日志未直接记录错误来源，不能按零错误通过。加载器之后补充分类诊断与已结束对局的重连检查，并在隔离小规模环境验证：已提交结束的对局单列为 endedDuringReconnect，取消仍计错误；旧结果不追溯改写。

单加载器基线约一核饱和，只达到约 12.65 Hz，输入 P95 为 240 ms；因此采用五进程对照。带宽仅包含消息体，未计网络及 TLS 开销，接近 0.7 Gbit/s 的流量必须纳入部署规格。完整对照、硬件、采样方法及误差见 [本机容量报告](capacity-local-2026-11-21.md)。

## 容量与正式开放尚未验收

容量脚本和协议客户端已实现，最终目标仍为接近生产的环境中持续 60 分钟、1,000 已登录连接、600 对局客户端、100 个满员房，公开/自定义混跑。各游戏进程每帧处理 P99 < 50 ms；真实 60 ms RTT 下输入至权威确认 P95 < 180 ms；网络恢复后可续局客户端 P95 < 5 秒。短时本机测试不能替代该验收，完整规格、带宽、错误率及复测数字由容量记录补充。
